## Why this milestone

The roadmap pins workstream #1 as "v0.2 finish: cut tag + CHANGELOG + visual demos + scope confirmation for query-based selection / `.label()`." Three things drive doing it now:

1. **The advertised surface is ahead of the runtime.** `SKILL.md` already documents `FaceSelector = CanonicalFace | string (label) | FaceQuery` and `EdgeSelector` accepts `{ face: string | FaceQuery }`. `src/intent/types.ts:27` declares `{ kind: 'label'; name: string }` as a first-class FaceRef variant. `src/capture/captureSession.ts:219` constructs label-kind refs from string face values. But there's no creation-side primitive — agents have no way to *declare* a label that the resolver can then look up. v0.2 finish closes that gap.
2. **The first per-module ship gate must execute end-to-end at least once.** The roadmap's "per-module ship gate" ritual (PR + two-pass code review + demo set + CHANGELOG entry + tag + reevaluation artifact) hasn't run cleanly yet — every prior version slipped one element. v0.2 is the smallest module to drive the full ritual through, with memorable-builds-policy in flight to enforce the demo half structurally.
3. **Build-in-public cadence.** Day 1 posts went out today (2026-05-04). Day 2's headline material is whichever ship lands next. A tag closure with a labeled-bracket demo is more substantive than a polish commit.

Anchor-property fit: `faceLabels` extends the agent-readable surface (anchor #1: agent-first) without introducing closures or dynamic eval (preserves anchor #2: MCP-native serializability). Labels live in feature options (anchor #3: AST-edit-primacy — round-trip clean through ts-morph). Three new error codes each get a HINTS entry (anchor #4: diagnostic-rigorous — sentinel stays green).

## Architecture decisions

### A1 — `faceLabels` declared at op site, persisted in `FeatureRecord.options`

Labels are an option key on creating operations, not a post-op chainable mutation:

```typescript
box([10, 10, 5], { faceLabels: { lid: 'top', base: 'bottom' } });
extrude(sketch, 5, { faceLabels: { rim: { atZ: 5, parallelTo: 'XY' } } });
```

`FeatureRecord` extended with `faceLabels?: Record<string, CanonicalFace | FaceQuery>`. ts-morph round-trip writes the object literal in canonical-key-sorted order so the AST output is deterministic. The JSON Schema for `add_feature` lists `faceLabels` per recognized feature kind.

**Why option-arg over chainable:** option-arg keeps labels structural (one record per feature, not one feature per label); preserves AST-edit-primacy because the serialized form matches the script form; fits the existing MCP `add_feature` shape (one tool call per feature, with all options in the args). Chainable forms (`.labelFace('top', 'lid')`) would either need a new feature kind that does no geometric work (anti-MCP-native — agents shouldn't see tools that don't move geometry) or mutate the upstream feature record after creation (anti-AST-edit-primacy — divergence between the script as-written and the IR).

### A2 — Resolution at consumer site reuses existing label-lowering plumbing

`src/backends/occt/edgeSelection.ts:507` already has a `resolveLabel(label: string, ...)` function that lowers labels to probe points. The gap is the *source*: that function expects a label table to look in, but no feature creates one. After A1 lands, the lowerer pulls the label table from each feature's `options.faceLabels` as it walks the feature graph at lowering time.

For canonical-alias entries (`{ lid: 'top' }`), resolve to the canonical name then dispatch to the existing canonical-ref walker. For query entries (`{ rim: { atZ: 5 } }`), resolve to a probe point at creation time (using `resolveFaceQuery` from `src/backends/occt/edgeQueries.ts:266`), persist the probe in the label table, and let the canonical-ref walker propagate it through the lineage. This means a label, once declared, behaves identically to a canonical ref through downstream operations — same lineage walker, same failure modes, same diagnostic codes.

### A3 — Three new error codes; canonical-ref errors apply transparently to labels

New codes (each gets a HINTS entry in the same commit per the structural sentinel rule):

| Code | Fires when | HINT content |
|---|---|---|
| `feature.label.undefined` | A consumer references a label string that no in-scope feature declared (e.g. `.fillet({ face: 'rim' })` but no upstream `faceLabels.rim` exists). | List the user labels declared by features upstream of the consumer in feature-ID order. |
| `feature.label.collision` | Two features upstream of the same consumer declare the same label. Resolution is ambiguous. | Name the conflicting feature IDs and the label string. |
| `feature.label.query-no-match` | A query-based label declaration matches zero faces at creation time (e.g. `faceLabels: { rim: { atZ: 999 } }`). | Print the canonical face names available on the originating shape. |

The existing canonical-ref errors (`feature.edge-feature.face-ref-ambiguous-after-split`, `feature.edge-feature.face-ref-removed`) apply transparently to labels because A2 routes labels through the same walker. No new codes needed for downstream lineage failures.

### A4 — `FaceQuery` polish: three additions, native shape

| New key | Type | Use case |
|---|---|---|
| `byNormal` | `'X' \| '-X' \| 'Y' \| '-Y' \| 'Z' \| '-Z'` | Direction-signed axis selector. The existing `parallelTo` is direction-blind — both `+Z` and `-Z` faces match `parallelTo: 'XY'`. `byNormal: 'Z'` matches +Z only. |
| `minArea`, `maxArea` | `number` (mm²) | Pick the largest face on a complex shape; filter out chamfer-result micro-faces; constrain by absolute size. |
| `boundingBoxIn` | `BoundingRegion` (existing type) | Face's bounding box must fit within the region. Symmetric with the existing `EdgeQuery.within`. |

`FACE_QUERY_KEYS` in `src/backends/occt/queryKeys.ts:27` gets the three additions; the compile-time exhaustiveness check (`type _FaceQueryKeysMissing = Exclude<keyof FaceQuery, typeof FACE_QUERY_KEYS[number]>`) guarantees `list_api` and the JSON schema stay in sync. Resolution is added inside `resolveFaceQuery`. Closure-based selectors are not added — see "Out" in Scope.

### A5 — Edge labels deferred to v0.3

The symmetric `edgeLabels: Record<userLabel, CanonicalEdge | EdgeQuery>` extension would land cleanly but pulls in an edge-canonical-name vocabulary decision (today only `top-rim`/`bottom-rim`-style names exist for box edges; cylinders, spheres, swept shapes have no canonical edge names). v0.3 owns `hole()` and `cut()` which *consume* edge refs heavily, so the canonical-name expansion lives there. v0.2 finishes the face-side story.

### A6 — `sphere` rejects `faceLabels` with a diagnostic

Spheres have no canonical face names and no meaningful query targets (every face is the single sphere surface). `faceLabels` on `sphere(...)` emits a fourth diagnostic code, `feature.label.unsupported-on-shape`, at capture time. Treated as an A3 sibling: ships with its own HINTS entry (HINT: list the operations that *do* accept `faceLabels`). The CHANGELOG entry under "Three new diagnostic codes" upgrades to four if this ships as a separate code; if implementation finds A3's `feature.label.query-no-match` already covers the sphere case (every query matches zero canonical faces because none exist), the fourth code collapses into the third — controller decides during plan-writing based on which produces the more actionable HINT.

### A7 — Closures explicitly excluded

`selectFaces(shape, f => f.normal[2] > 0.99)` is not added. Reasons: (1) closures don't JSON-serialize, so MCP agents can't construct them; (2) executing arbitrary closures on the kernel side would require `eval` or function-string transmission, both security smells; (3) the descriptor type `FaceQuery` covers every realistic predicate after the A4 additions. If a corner case appears later, the answer is to add the missing predicate to `FaceQuery`, not to escape-hatch into closures.

## Risks

1. **Lineage walker corner cases on query-based labels.** Canonical refs walk back to a primitive's named face; query-based labels resolve to a probe point at creation time. A subsequent transform that significantly distorts geometry (non-uniform scale → curves bend) could push the probe off-face. Mitigation: probe-resolution after each transform recomputes the closest-face hit; tolerance set per existing canonical-ref convention. If a real failure surfaces, fall back to `feature.label.query-no-match` after lineage walk.
2. **Memorable-builds-policy PR slip.** v0.2 finish blocks on policy merge. If policy review takes more than a day, reorder: write the v0.2 finish spec + plan now (no code), implement once policy lands. The spec doc itself is fine to write either way.
3. **`whats-new.md` template churn.** Memorable-builds-policy spec defines the three required sections; if those section names change in review, the three v0.2 demo `whats-new.md` files need a follow-up edit. Mitigation: write `whats-new.md` files only after policy PR merges to develop.
4. **Eval task ranking shift.** Adding two new corpus tasks may shift cookbook BM25 rankings. Mitigation: snapshot test in `eval/cookbook.test.ts` already gates ranking changes; if it fails on the new tasks, re-baseline with explicit rationale (matches the discipline used when cookbook v1 added eval tasks).
