# v0.2.0 — Tracked Face/Edge Refs Across Transforms + Booleans — Design Spec

**Goal:** Close NORTHSTAR's v0.2 module. Face and edge identity is preserved across every transform and every boolean operation in the unambiguous case. Existing scripts that today fail with `feature.edge-feature.face-ref-not-resolvable` after a transform or boolean now succeed with no script-side syntax change. The "Critical Constraint" section in SKILL.md is deleted.

**Architecture:** A per-shape `HistoryMap` tracks each face/edge back to its originating primitive's canonical name (or sketch label). Boolean and edge-feature operations bypass Replicad's wrappers to read OCCT's `BRepAlgoAPI_*::Generated/Modified/IsDeleted` callbacks directly. Transforms preserve identity 1:1 via parallel `TopExp_Explorer` walks. Resolution = walk back to originating primitive, resolve canonical name, walk forward through history; 1 child = success, 0 = removed-error, >1 = ambiguous-error.

**Tech Stack:** TypeScript 5.9, OCCT WASM via `replicad-opencascadejs` (direct access at history-tracked sites; bypasses Replicad's `Shape3D.fuse/cut/intersect` wrappers since they discard the OCCT builder before history can be read). vitest 4 for tests. No new npm dependencies.

**Spec lineage:** Implements the `tracked` half of NORTHSTAR §Stable Naming. Geometry-snapshot fallback for ambiguous splits and `created` face refs (NORTHSTAR's v0.3 module) are explicitly out of scope.

---

## Why this milestone

The current `feature.edge-feature.face-ref-not-resolvable` diagnostic fires every time an agent writes the natural form `box(...).translate(5, 0, 0).fillet(2, { face: 'top' })`. The workaround documented in SKILL.md ("apply edge feature *before* transforms") is awkward, easy to forget, and incompatible with composing primitives — there's no workaround at all for filleting a face on a `subtract()` result. The "Canonical Face Refs — Critical Constraint" section in SKILL.md is the largest single block of caveats in the agent-facing skill doc; it consumes ~50 lines explaining a limitation that should not exist in a parametric CAD platform.

Closing this is the highest-impact agent-facing change available in the current backlog:

- It eliminates the most-cited diagnostic failure mode in agent workflows
- It removes a documented workaround that adds cognitive load
- It enables natural composition (`subtract → fillet`, `translate → chamfer → mirror`)
- It unblocks future work that depends on stable face identity (e.g., `hole`/`cut` as first-class features in v0.3, where the cylindrical wall of a hole becomes a `created` face ref)

NORTHSTAR §Stable Naming explicitly anticipated this work: "v0.1 ships only `canonical` face/edge refs (top/bottom/left/right/front/back). `tracked`/`created`/`propagated` refs and the `NamingHistory` walk are v0.2+ work." This milestone delivers the `tracked` half. The `created`/`propagated` halves (which require geometry-snapshot fallback for genuinely-ambiguous cases) defer to v0.3 per NORTHSTAR's split.

This is a **single-PR ship** discipline-bound milestone: v0.2.0 ships only when the entire matrix (every transform × every boolean × every edge feature × every input shape category) passes the integration test suite. No staged rcs.

## Architecture decisions

### A1 — `HistoryMap` lives on `OcctBackend` (the shape itself), not as a separate module

Each `OcctBackend` instance carries a `historyMap: Map<FaceHash, FaceLineage>` field, where the key is the OCCT face hash (`TopoDS_Shape::HashCode()`) of a face on the current shape, and the value is its lineage record (originating primitive, originating canonical name or sketch label, originating feature ID).

When an operation creates a derived shape, the new `OcctBackend` builds its `historyMap` from its input(s)' `historyMap` plus the new operation's history-callback results. NamingHistory-as-a-separate-module (per NORTHSTAR's literal text) becomes implicit — "the union of all live `OcctBackend.historyMap` instances" — because resolution is single-shape-deep in v0.2 (a fillet sees its immediate input shape's `historyMap`; the originating primitive feature is reachable via `inputs.base.historyMap`'s lineage records).

**Rationale.** Promotable to a real `src/naming/` cross-shape module in v0.3 when geometry-fallback needs cross-shape lookup. For v0.2, keeping the data inline avoids over-engineering and matches how the lowerer already structures its work (one OcctBackend per feature output).

### A2 — Direct OCCT WASM access at boolean and edge-feature sites; bypass Replicad's wrappers

Replicad's `Shape3D.fuse/cut/intersect` (in `node_modules/replicad/dist/replicad.js:3273-3337`) discard the `BRepAlgoAPI_*` builder before history can be read. The builder holds the `Generated/Modified/IsDeleted` maps; once it goes through `GCWithScope`, those maps are gone.

We construct the builder ourselves in the new helpers:

```typescript
// src/backends/occt/historyAwareBooleans.ts (sketch)
export function cutWithHistory(body: OcctBackend, tool: OcctBackend): {
  shape: TopoDS_Shape;
  inputFaceHistory: Map<FaceHash, FaceHash[]>;  // body face → output children
  toolFaceHistory: Map<FaceHash, FaceHash[]>;
  inputEdgeHistory: Map<EdgeHash, EdgeHash[]>;
  toolEdgeHistory: Map<EdgeHash, EdgeHash[]>;
  deletedInputFaces: Set<FaceHash>;
  deletedToolFaces: Set<FaceHash>;
} {
  const OC = getOC();
  const progress = new OC.Message_ProgressRange_1();
  const cutter = new OC.BRepAlgoAPI_Cut_3(body.wrapped, tool.wrapped, progress);
  cutter.SetToFillHistory(true);
  cutter.Build(progress);
  // ... iterate TopExp_Explorer over body and tool, query Modified/Generated/IsDeleted ...
  // ... DO NOT call SimplifyResult — see trade-off below ...
  const resultShape = cutter.Shape();
  cutter.delete();
  progress.delete();
  return { shape: resultShape, ...maps };
}
```

The pattern follows the existing `worker.ts:275-312` cylinder-detection code that already bypasses Replicad for direct OC access. Same approach for `BRepFilletAPI_MakeFillet`, `BRepFilletAPI_MakeChamfer`, `BRepOffsetAPI_MakeThickSolid` (all expose `Generated/Modified/IsDeleted`).

**Trade-off.** Skip `cutter.SimplifyResult()` at history-tracked sites. Replicad calls this unconditionally to merge coplanar faces; merging mutates the result topology and invalidates the history maps. Skipping it may leave extra faces in the result.

For v0.2 this is accepted as a known cosmetic trade-off; downstream consumers (mesh export, edge selection still works, volume calculation) tolerate extra faces. R2 in the risks section documents the measurement plan and the fallback (re-apply SimplifyResult after extracting the historyMap, with a hash-remap step).

### A3 — Transforms preserve face identity 1:1; no `BRepAlgoAPI_*` history needed

`translate`, `rotate`, `scale`, `reflect`, `mirror` are rigid-body or affine operations that preserve topology — same face count in input and output, no splits, no merges. We iterate `TopExp_Explorer` over input and output in parallel; the i-th input face maps to the i-th output face.

OCCT preserves topology order across these operations. The `propagateTransformHistory(input, op): HistoryMap` helper is purely mechanical — for each face in the input historyMap, look up its index, find the corresponding output face hash, copy the lineage record under the new hash key.

**Rationale.** Avoids unnecessary OCCT history-callback overhead for the common case (most agent scripts apply many transforms, few booleans). Keeps transform lowering simple and fast.

### A4 — Resolution algorithm: walk back to originating primitive, walk forward through history

Given `{face: 'top'}` on a current `OcctBackend`:

1. **Walk back** through `inputs.base` chain to find the originating primitive (a `box`/`cylinder`/`sphere` feature, OR a sketch-extrude/sweep/loft/revolve which has its own labeling system). Record the chain of operations traversed.
2. **Resolve at the root.** Use the existing canonical resolver (`canonicalBoxFaceEdges` / `canonicalCylinderEndCapEdges`) on the originating primitive's shape. Returns a starting face hash.
3. **Walk forward** through every operation in the chain. At each step, look up the current face hash in the operation's history-derived map; replace with the successor face hash(es). Track the count.
4. **Final disposition** based on count of resolved hashes:
   - **1 hash** → return it (success — most common case)
   - **0 hashes** → emit `feature.edge-feature.face-ref-removed` diagnostic (or `face-feature.*` parallel for shell)
   - **>1 hashes** → emit `feature.edge-feature.face-ref-ambiguous-after-split` diagnostic

The `base.kind` guard at `edgeSelection.ts:134` and `:393` is removed entirely — the new resolver handles transformed and boolean-derived shapes. The existing canonical-refs-on-un-transformed-primitive path becomes a degenerate case of the same algorithm (zero operations to walk forward through).

### A5 — Diagnostic surface change

| Code | New / Existing | Reachability | What it means |
|------|----------------|--------------|---------------|
| `feature.edge-feature.face-ref-ambiguous-after-split` | NEW | `engine-path` | The named face was split into N>1 children by an upstream operation. Geometry-fallback disambiguation ships in v0.3.0 |
| `feature.edge-feature.face-ref-removed` | NEW | `engine-path` | The named face was removed by an upstream operation. Reference a different face that still exists in the current shape |
| `feature.face-feature.face-ref-ambiguous-after-split` | NEW | `engine-path` | Same as edge-feature parallel; for `.shell()` |
| `feature.face-feature.face-ref-removed` | NEW | `engine-path` | Same as edge-feature parallel; for `.shell()` |
| `feature.edge-feature.face-ref-not-resolvable` | EXISTING | `engine-path` | **Stays** but only fires for genuinely-unsupported ref kinds (non-canonical, non-label, non-query, non-tracked). The "transformed primitive" trigger goes away |
| `feature.face-feature.face-ref-not-resolvable` | EXISTING | `engine-path` | Same |

The 4 new codes get HINTS entries with v0.3 deferral language for the ambiguous case and clear actionable language for the removed case. The rc.17 hints-coverage sentinel will catch any missing entry at CI time.

### A6 — `tracked`/`created`/`propagated` FaceRef variants stay as internal-only types

The FaceRef type already declares these variants. v0.2 leaves them as **declared but not user-creatable** — no script-side API emits them. They will become user-creatable in v0.3+ when `created` ref support ships (for naming faces newly introduced by boolean operations) and `propagated` ref support ships (for explicit cross-feature face naming).

The HINTS classification updates from "reserved for v0.5+" to "internal-only / not yet user-creatable in v0.2; coming in v0.3+".

## Open questions resolved at the top of this plan

1. **Scope** — NORTHSTAR-as-written. v0.2.0 ships when unambiguous cases work end-to-end; ambiguous splits and deleted faces produce clear diagnostics with v0.3 deferral language. Not "all face cases work" (that's v0.3 with geometry fallback).
2. **API model** — Invisible. `{face: 'top'}` keeps the same script-side syntax. Internal resolver walks history. The `tracked`/`created`/`propagated` FaceRef variants stay declared but not user-creatable in v0.2.
3. **Failure-mode policy** — Hard error with two distinct new diagnostic codes per ambiguous and removed case (4 total across edge-feature and face-feature surfaces). Distinct codes give agents structured information about whether to wait for v0.3 or fix the script.
4. **History-callback feasibility** — Confirmed: OCCT WASM exposes `BRepAlgoAPI_*::Generated/Modified/IsDeleted` directly via `replicad-opencascadejs`. kernelCAD already has the bypass-Replicad pattern (`worker.ts:275`). No fork needed.
5. **`SimplifyResult` trade-off** — Skip at history-tracked sites. R2 measures the cosmetic impact and provides a fallback if regression appears.
6. **Where the history machinery lives** — `src/naming/` directory (matches NORTHSTAR repo plan). Inline on `OcctBackend` for the per-shape map; promotable to a separate `NamingHistory` module in v0.3 if cross-shape lookup needs warrant it.

## Risks

- **R1 (high):** OCCT face hashes are unstable across recompiles or WASM module reloads. Mitigation: hashes are stable WITHIN a single WASM session — that's all v0.2 needs. Cross-session persistence is a v0.3+ concern (geometry-fallback uses geometric properties, not hashes).

- **R2 (medium):** Skipping `SimplifyResult()` produces shapes with extra coplanar faces that confuse downstream consumers (mesh export, edge counts, volume calc). Mitigation: measure via integration tests on a corpus of 5-10 representative scripts (Task 13); if any volume/edge-count regression appears, add a separate `simplifyAfterHistoryRead()` step that re-applies SimplifyResult AFTER we've extracted the historyMap and includes a hash-remap pass against the simplified topology.

- **R3 (medium):** Some edge features (e.g., `BRepFilletAPI_MakeFillet`) may not consistently fill `Generated/Modified/IsDeleted` for ALL faces of the input solid — they may only report changed ones. Mitigation: the resolver's walk-forward step assumes "input face X with no entry in history map → unchanged → use same hash in output." Verified by Task 3 unit tests.

- **R4 (low):** A fillet on a face that's about to be filleted again (e.g., `box.fillet(2, {face:'top'}).fillet(1, {face:'top'})`) — the second fillet's input has a "top" face but it's been geometrically modified. The historyMap should still resolve correctly because the canonical name is preserved through the lineage chain. Add specific test for this case in Task 12 matrix.

- **R5 (low):** Performance overhead of building historyMap at every operation. Per-operation cost ≈ `O(face_count + edge_count)`. For typical agent scripts (~5-15 features, each shape ~10-50 faces), this is sub-millisecond and negligible. Mitigation: only optimize if Task 12 measurements show >5% regression on representative scripts.

- **R6 (low):** A future Replicad upgrade changes the internal `Shape3D.cut` implementation in a way that breaks our `(shape as any).wrapped` access pattern. Mitigation: pin Replicad version (already done — `0.20.5`); document the dependency in `historyAwareBooleans.ts`'s file-level comment; if the API breaks on a future upgrade, the test matrix (Task 12) catches it immediately.

## What this milestone is NOT

- Not a feature release in the "new user-facing API" sense. Zero new script syntax. The user-visible change is "scripts that fail today with `face-ref-not-resolvable` now succeed; scripts that succeed today still succeed."
- Not a quality pass. This is a real architectural addition (HistoryMap, EvolutionRecord, the resolver) — it's a feature in the semver "minor version bump" sense, just not in the "new API surface" sense.
- Not the geometry-fallback work. Ambiguous splits stay deferred to v0.3 with clear diagnostics. NORTHSTAR's deliberate v0.2 / v0.3 split is honored.
- Not a UI / studio milestone. Kernel-only.
- Not gated on npm publish of v0.1.0. The two milestones are independent — v0.2.0 can ship as a tag + git history even if v0.1.0 hasn't been published yet (and vice versa). When both are ready and the user is ready to publish, both go to npm in version order.
