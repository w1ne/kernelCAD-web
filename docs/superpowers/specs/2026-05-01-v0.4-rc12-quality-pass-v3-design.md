# v0.4-rc.12 Quality Pass v3 — Design Spec

**Goal:** Close the rc.11 review punch list (1 Critical-class + 8 Important findings) and clear pre-existing competitor-reference debt across the repo. No new user-facing features.

**Architecture:** Eight focused, mostly-independent tasks. Two are infrastructure (bundle sentinel, banner alignment), three are mechanical refactors (helper extraction, helper export, hint surfacing), two are testing gaps (chamfer e2e, face-wrapper geometric verification), one is a written architecture memo, and one is a repo-wide text sweep. The milestone is a refactor + harden pass — no kernel behavior changes.

**Tech Stack:** TypeScript, esbuild, vitest, Replicad/OpenCascade WASM. No new dependencies.

---

## Why this milestone

The rc.11 review surfaced one critical class of regression (silently-skipping bundle test) plus eight Important findings. The hotfix during rc.11 (esbuild banner colliding with `createRequire` import) demonstrated that the `actually use what you ship` discipline is correct but is currently a manual checklist, not a CI gate. rc.12 encodes that discipline as a non-skippable test, fixes the banner collision at its root, and pays down accumulated review fixes before they compound into a larger refactor.

A pure quality milestone is also the natural home for the competitor-reference sweep. Per the memory rule that "spec/plan/code/CHANGELOG must be framed as native kernelCAD, not as matches-X / improves-over-Y," ten existing references (1 in source, 9 in CHANGELOG and similar) must be re-framed.

## Architecture decisions made during brainstorming

These were resolved before spec write-up. They lock the spec; the plan should not re-litigate them.

### A1 — Banner alignment over alias retention

**Decision.** Align `package.json:16` build:cli banner from `'module'` to `'node:module'`, then revert the rc.11 hotfix alias in `src/mcp/server.ts:7` to a plain `import { createRequire }`.

**Why.** The alias is a per-file workaround for a structural mismatch. Aligning the banner with the source convention used everywhere else in the repo means future files that import `createRequire from 'node:module'` won't collide with the bundle. The hotfix comment block becomes a tombstone documenting the historical fix.

**Why not the modernization path.** Replacing `createRequire` with `import pkg from '../../package.json' with { type: 'json' }` (TS 5.3+ / Node 22+) was discussed and deferred. esbuild's handling of import attributes under `--platform=node --format=esm` has edge cases worth verifying separately. rc.13+ may revisit. rc.12's banner alignment is the smaller, lower-risk fix.

### A2 — Hint reachability label, not engine refactor

**Decision.** Add a `reachable` field to `whyDidThisFail` hint entries. Three values: `'engine-path'` (fires through normal evaluation), `'direct-lowerer-only'` (only fires if the lowerer is invoked directly, not through the engine), and `'reserved'` (forward-looking, no current trigger). Mark `feature.loft.bad-sketch` and `feature.sweep.multi-face-profile` accordingly.

**Why.** The diagnostic surface should not lie to agents. Marking unreachable codes lets agents that consume `list_api`-style introspection filter or weight the codes correctly. Touches the hint table only — no engine, no lowerer, no recompute change.

**Why not engine participation in missing-input diagnosis.** Letting downstream lowerers receive a missing-input sentinel and emit feature-specific codes is a real architecture change to `RecomputeEngine`. It belongs in rc.13+ after a written design memo (also in rc.12 scope, see Component 8).

### A3 — Competitor sweep covers source + CHANGELOG

**Decision.** Clean every `ForgeCAD`, `Fusion 360`, `OnShape`, `CadQuery` reference in `src/`, `tests/`, `CHANGELOG.md`, and `README.md`. Replicad references stay (it is the backend dependency, not a competitor). Clean both forward-going and historical CHANGELOG entries — the memory rule explicitly names CHANGELOG.

**Why.** Memory-rule debt only grows. A pure-quality milestone is the natural home for non-functional cleanup; bundling it into a feature milestone would be ad-hoc. Cost is bounded — text-only edits, no behavior change.

## Components

### Component 1 — Bundle-startup sentinel test (closes C1)

**Where.** New file `tests/integration/cli-bundle/startup.test.ts`.

**What it does.** A non-skippable vitest integration test that:
1. Asserts `dist/cli/index.js` exists. If it does not, the test FAILS (not skips).
2. Spawns the bundle via `node dist/cli/index.js` with whatever subcommand starts the MCP server (plan-time work to confirm the exact invocation against current CLI surface).
3. Asserts the spawned process boots without crashing within a bounded timeout — no immediate exit with non-zero code, no fatal stderr. The exact "boot succeeded" signal (server-init handshake response, ready-line on stderr, port-listening, etc.) is plan-time work to match the existing `tests/integration/mcp/spawn.test.ts` pattern.

**Why non-skippable.** The rc.11 bundle crash (`SyntaxError: Identifier 'createRequire' has already been declared`) sailed past `npm test` because the existing `tests/integration/mcp/spawn.test.ts:84` uses `describe.skipIf(!existsSync(CLI_BIN))`. Skipping when the bundle is missing means a missing build is invisible. The new sentinel makes that case fail loudly.

**Build-time integration.** Either:
- (Preferred) Add `npm run build:cli` to the `pretest` script in `package.json` so `npm test` builds before running. The sentinel then asserts presence after the build step.
- (Fallback) Have the test itself run `npm run build:cli` in `beforeAll` if `dist/cli/index.js` is missing. Slower but self-contained.

The plan picks one based on existing test setup conventions.

**What this test guards against.** Any future bundle-only regression: missing exports, incompatible bundle format, ESM/CJS interop bugs, banner conflicts, transitive runtime crashes. It does NOT replace the existing source-tested unit and integration suites — it is a smoke test that the *shipped artifact* boots.

### Component 3 — Export `isSameEdge` and de-duplicate edge matching (closes I3)

**Where.**
- `src/backends/occt/edgeQueries.ts` — change `isSameEdge` from file-private to a named export. Add a JSDoc comment documenting the `1e-6` tolerance and its mm-scale assumption.
- `src/backends/occt/occtBackend.ts:528-538, 553-563` — replace inline `eq` functions in `filletVariable` and `chamferVariable` with `isSameEdge` calls.

**Tolerance documentation.** `isSameEdge`'s comment must state that `1e-6` is mm-scale (1 nm) and that callers working at radically different scales (e.g. astronomical-units or atomic-scale CAD) need to revisit. Today, kernelCAD is mm-scale across the board — this is documentation, not parameterization.

**No behavior change.** The replacement is structurally identical. Verified by the existing `variableFillet.test.ts` suite continuing to pass with no measurement changes.

### Component 4 — Extract `applyVariableEdgeFeature` helper (closes I4)

**Where.** `src/backends/occt/occtLowerer.ts` — the `case 'fillet':` and `case 'chamfer':` arms each have a ~40-line variable-radius branch. Both branches build the same synthetic FeatureRecord shape, run the same per-group `pickEdges` resolution loop, emit the same diagnostic codes (`empty-groups`, `invalid-group`), and call backend `filletVariable`/`chamferVariable`.

**Helper signature** (final form will be locked in the plan):

```typescript
function applyVariableEdgeFeature(
  kind: 'fillet' | 'chamfer',
  base: Shape,
  feature: FeatureRecord,
  records: ReadonlyMap<FeatureId, FeatureRecord>,
  occt: OcctBackend,
): { shape?: Shape; diagnostics: Diagnostic[] };
```

**What stays in the lowerer arms.** Each arm checks `metadata.variable === true`; if true, it delegates to the helper and returns the result. If false, it falls through to the existing single-radius logic. The arms shrink from ~50 lines each to ~10.

**Diagnostic prefix handling.** The helper takes the `kind` parameter and produces correctly-prefixed codes (`feature.fillet.empty-groups` vs `feature.chamfer.empty-groups`).

**No behavior change.** Same test suite (`variableFillet.test.ts`, plus the lowerer integration tests) must pass unchanged.

### Component 5 — `chamferVariable` end-to-end fixture (closes I5)

**Where.** New file `tests/e2e/fixtures/bracket-bevels.kcad.ts`.

**Shape of the fixture.** Mirrors `bracket-blends.kcad.ts` but uses `chamfer([{ edges, distance }, ...])` form. Produces a 2-group variable-distance bevel on a parameterized box. Param surface — `Length`, `Width`, `Thickness`, `TopDistance`, `BottomDistance` — same conventions as the bracket-blends fixture.

**Test coverage.** The `cli-acceptance.test.ts` discovery loop should pick it up automatically. Verify diagnostics array is empty; verify a non-zero volume.

**Why a separate fixture, not a combined fillet+chamfer one.** Single-feature fixtures keep failure attribution clear when geometry regressions land. Combining would obscure which form regressed.

### Component 6 — Face-wrapper variable-fillet geometric integration test (closes I6)

**Where.** Extend `tests/integration/backends/occt/variableFillet.test.ts` (or its integration sibling — plan picks based on existing structure).

**What it covers.** rc.11's variable-radius capture tests verify that `Shape.fillet([{edges: {face: 'top'}, radius: 1}])` produces an `inputs.edge_group_0` slot in the FeatureRecord. The lowerer code path for resolving a face-wrapper input (the `rawRef.kind === 'face'` branch in the synthetic-record dispatch) is **not currently exercised end-to-end**.

**Test shape.** Build a 10×10×5 box, apply variable-fillet using `{face: 'top'}` selector + `radius: 1`. Assert: (a) no diagnostics, (b) volume ≈ analytic expected (top-face filleted, bottom + sides unmodified), (c) shape has reduced surface area at the top edge ring.

**Why this matters.** Agents using face-wrapper selectors for variable-radius are a primary use case (`top edge of this bracket gets a bigger fillet than the bottom`). Today, the only tests of that path are at the FeatureRecord level — geometry could silently regress.

### Component 7 — `reachable` field on `whyDidThisFail` hints (closes I8)

**Where.** `src/mcp/tools/whyDidThisFail.ts` — the hint table.

**Schema change.** Each hint entry gets a new field:

```typescript
type HintEntry = {
  code: string;
  hint: string;
  reachable: 'engine-path' | 'direct-lowerer-only' | 'reserved';
};
```

**Initial classification.** Plan-time work, but the framework:
- `'engine-path'` — fires during normal recompute. The vast majority of existing codes.
- `'direct-lowerer-only'` — would only fire if the lowerer is invoked directly (not through the engine). Today, `feature.loft.bad-sketch` and `feature.sweep.multi-face-profile` qualify. Marking them honestly closes I8.
- `'reserved'` — codes that have no current trigger anywhere. None at rc.12 ship; reserved for rc.13+.

**Wire format change.** The MCP `why_did_this_fail` tool should include `reachable` in its response payload so agent consumers can see it. Update the tool's response schema.

**SKILL.md update.** Document the field briefly so agents reading the skill doc know it exists. One paragraph.

### Component 8 — Error attribution policy memo (closes I7)

**Where.** New file `docs/superpowers/specs/2026-05-01-error-attribution-policy.md`.

**Length.** ~200–400 words. Not a full design spec. A position document.

**What it covers.**
1. Statement of the current behavior — `RecomputeEngine` short-circuits with `recompute.input.missing` when an upstream input is missing, before downstream lowerers run. As a result, downstream feature-specific codes for missing-input cases (`feature.loft.bad-sketch`, future `feature.sweep.bad-sketch` etc.) are unreachable through the engine path.
2. Statement of the trade-off — root-cause-first attribution (current) vs feature-specific attribution (proposed).
3. Position taken — for rc.13+ we will evaluate whether `RecomputeEngine` should let lowerers opt into receiving a `MISSING_SHAPE_SENTINEL` so they can emit feature-specific diagnostics. Not committed; flagged for design work.
4. Rule for forward-looking codes — any new diagnostic code that is currently unreachable through the engine path must be marked `'direct-lowerer-only'` or `'reserved'` per Component 7.
5. Rule for citation — future "forward-looking" diagnostics must cite this memo at the PR/spec level so the pattern is visible, not normalized into invisibility.

**Effect.** This memo is read-only artifact. It does not change kernel behavior. It serves as the citation that future PRs reference instead of re-litigating the policy each time.

### Component 9 — Competitor-reference sweep (closes memory-rule debt)

**Files affected.** Confirmed via repo grep:
- `src/mcp/server.ts:86` — 1 hit (`Mirrors ForgeCAD's edgesOf()`)
- `CHANGELOG.md` — 7 hits (`ForgeCAD` references in rc-history entries plus 1 `Fusion 360` in older Scene Browser entry)

**Edit policy.**
- **Source code:** rewrite to native framing. e.g. `"Mirrors ForgeCAD's edgesOf(). ..."` → `"Returns the boundary edges of a named canonical face. ..."` — drop the comparator clause.
- **CHANGELOG:** rewrite each affected line to native framing. Two reasonable approaches:
  - (Preferred) **Edit-in-place each historical entry.** Preserves the rest of the entry, removes only the comparator phrasing. The CHANGELOG narrative reads as native kernelCAD design throughout.
  - (Alternative) **Add a one-line policy header at the CHANGELOG top** ("Note: entries prior to rc.12 may reference comparator products; the project policy from rc.12 onward is native framing") and skip historical edits. Less invasive but leaves debt visible.

  The plan picks edit-in-place — the memory rule explicitly names CHANGELOG, and partial compliance is a worse signal than full compliance.

**No grep-and-replace shortcut.** Each replacement is contextual. A `sed -i 's/ForgeCAD//g'` across the file would leave grammatical wreckage. Plan-time work edits each line by hand.

**Re-grep after sweep.** After the edits, `grep -rn -E "ForgeCAD|Fusion 360|OnShape|CadQuery" src/ tests/ CHANGELOG.md README.md` must return zero hits. Add this as a final verification step in the plan.

**Replicad excluded.** Replicad is the backend dependency (the OpenCascade-WASM wrapper kernelCAD ships on top of). References to Replicad are technical, not comparator. Leave them.

## Testing strategy

The milestone is fundamentally a refactor + harden pass. The test coverage strategy:

- **Existing tests must continue to pass unchanged** — Components 2, 3, 4 are pure refactors. No new test cases beyond what's already there. If something breaks, the refactor was wrong.
- **One new e2e fixture** — Component 5 (`bracket-bevels.kcad.ts`).
- **One new geometric integration test** — Component 6 (face-wrapper variable-fillet).
- **One new bundle-startup sentinel** — Component 1.
- **No tests for Components 7–9** — Component 7 is a typing / data change; Component 8 is a written memo; Component 9 is text edits. The "test" for Component 9 is the post-edit `grep` returning zero hits.

After the milestone, the pre-merge gate should be: `npm run qc:full` (typecheck + lint + test + build:cli + bundle-startup sentinel). Today `npm test` may not include build:cli in its pre-step — Component 1 makes this concrete.

## Open questions for the spec reviewer

1. **Pretest hook vs in-test build.** Component 1 needs a build step before the sentinel runs. Putting `build:cli` into `pretest` slows down every `npm test` run by the bundle build time. Alternative: keep `npm test` fast, run the sentinel only under `npm run qc:full`. Plan should pick one based on observed bundle-build wall time.

2. **Historical CHANGELOG edit-in-place vs policy-header.** Spec preference is edit-in-place, but spec reviewer may prefer policy-header to preserve historical narrative. Plan should default to edit-in-place per spec; reviewer can override during plan review.

3. **`reachable` field default.** For hints not explicitly classified, what's the default — `'engine-path'` (optimistic, may lie) or `'engine-path'` with a lint warning if any hint is missing the field (forces classification at code-write time)? Plan should pick the strict variant.

These do not block plan-writing; they are flagged to the reviewer as judgment calls.
