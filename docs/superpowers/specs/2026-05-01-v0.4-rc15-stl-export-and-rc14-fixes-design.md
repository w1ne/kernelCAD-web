# v0.4-rc.15 — `export_stl` MCP tool + bundled rc.14 review fixes — Design Spec

**Goal:** Add the `export_stl` MCP tool so agents can ship geometry to downstream workflows; close the rc.14 review punch list (6 Important + 2 selected Nits).

**Architecture:** Bundled feature + quality milestone matching the rc.10/rc.11/rc.13 cadence. The feature wraps the existing CLI-side export pipeline as an MCP tool. The review-fix block completes patterns rc.14 introduced (drift-sentinel coverage, validation-layer consistency, KernelError construction discipline).

**Tech Stack:** TypeScript 5.9, Replicad 0.20.5 (provides STL mesh export), vitest 4. No new dependencies.

---

## Why this milestone

**The feature side.** Today, kernelCAD agents can produce geometry (in-memory `Shape` objects), measure it (volume, bbox, surface area), and introspect it (`list_edges`, `list_faces`, `list_topology`). They **cannot** get geometry out to other tools — slicers, simulators, viewers, file-share. The CLI command `kernelcad export stl <file> -o <out>` exists; agents talking through MCP have no equivalent.

`export_stl({ file? | code?, output_path })` closes the output-workflow gap. The MCP tool runs the same export pipeline the CLI command uses, writes the result to `output_path`, and returns a small JSON receipt (`{ ok, output_path, byte_count, feature_count, diagnostics }`). Agents can now build a geometry, save it, then hand the path to a downstream tool — completing the workflow that CAD authoring is normally embedded in.

**The quality side.** The rc.14 review surfaced 6 Important findings and 8 Nits, all bounded pattern-completion items rather than urgent fixes. Bundling them in rc.15 matches the established cadence and prevents the punch list from accumulating.

## Architecture decisions made before spec write-up

### A1 — `export_stl` writes server-side; `output_path` is required

**Decision.** `export_stl({ file? | code?, output_path: string })` — `output_path` is a required parameter. The MCP tool runs the export pipeline, writes the binary STL to that path, and returns a receipt. No inline-content variant in v1.

**Why.** Matches the CLI pattern (`kernelcad export stl <file> -o <out>`). Agents who want inline content can be served in rc.16+ if usage demand surfaces. Inline base64 for 50KB-1MB STL files is ugly in JSON-RPC; server-side write is the standard MCP file-op pattern. Existing MCP tools that DO return content inline (`set_param_value`, `add_feature`, `remove_feature`) handle small text — STL is a different size class.

### A2 — Validation-layer policy (closes I-3, I-4): capture-time throws across all rigid-body transforms

**Decision.** All rigid-body transform methods on Shape (`translate`, `rotate`, `scale`, `reflect`, `mirror`) validate their arguments at capture time and throw `KernelError` with a feature-namespaced code if invalid. The lowering-time gates added in rc.14 (`feature.transform.invalid-plane`) become forward-looking infrastructure — they cover direct-IR-construction paths but won't fire through normal capture.

**Why.** rc.14's `Sketch.reflect` precedent is the agent-first answer: agents debugging benefit from script-line precision in stack traces. Lowering-time-only validation produces diagnostics with `featureId` but no script line. Extending the capture-time pattern across all transforms gives uniform ergonomics. The rc.14 lowering-time gates stay (they're cheap and cover edge cases) but are reclassified `'reserved'` in the reachability table.

The capture-time validators throw `KernelError` with codes like:
- `feature.transform.invalid-translate` (Vec3 finite-numbers check)
- `feature.transform.invalid-rotate` (Vec3 axis + finite-degrees check)
- `feature.transform.invalid-scale` (positive-finite scalar OR Vec3 of positive-finite numbers)
- `feature.transform.invalid-reflect` (PlaneSpec — already exists at lowering-time, mirror to capture-time)
- `feature.transform.invalid-mirror` (PlaneSpec — already exists at feature-time as `feature.mirror.invalid-plane`; the new code is the transform-line precise variant; the feature-side stays for clarity at the diagnostic-cause layer)

### A3 — `KernelError.featureId` is constructor-injected (closes I-5, I-6)

**Decision.** `new KernelError(code, message, featureId?)`. The mutable post-construction field goes away. `kernelErrorToDiagnostic`'s optional `featureId` parameter is dropped — the function reads from `e.featureId` on `KernelError` instances; non-KernelError throws (where the caller may have feature context) get the `featureId` via a different shape (passed as a separate diagnostic field by the catch site, not via the error object).

**Why.** Constructor injection is structurally honest — the type signature tells you "this error can carry a feature id," and there's no moment where the error exists with `undefined`-then-set. Drops the precedence ambiguity from I-6 entirely (one path: throw site sets it). All existing throw sites in `Sketch.reflect` and elsewhere can be updated mechanically (~5 sites total).

### A4 — Drift-sentinel coverage extends to all `listApi.ts` exports + factor `escapeRegExp` (closes I-1, I-2)

**Decision.** Add `skillGlobalsDrift.test.ts` and `skillPathBuilderMethodsDrift.test.ts` parallel to the existing two. Factor `escapeRegExp` into `tests/unit/skill/_helpers.ts` (or similar). All six sentinels (4 SKILL.md + 1 docs + 1 reachability) import from one helper.

**Why.** rc.14's drift-sentinel strategy is "the agent-discoverable surface cannot drift undetected." rc.14 sealed Shape methods, Sketch methods, MCP tool count, and diagnostic codes — but not GLOBALS (14 entries: `box`, `cylinder`, `sphere`, `extrudeRect`, `path`, `param`, `helix`, `selectEdges`, etc.) or PATH_BUILDER_METHODS (9 entries: `moveTo`, `lineTo`, arcs, `label`, `close`). Closing the gap is mechanical. Factoring the helper removes 5+ duplicates of one tiny function.

### A5 — `cli.*` reachability classification (closes N-1)

**Decision.** Add a fourth `HintReachability` value: `'cli-path'`. Reclassify `cli.script.exception`, `cli.file.read`, `cli.no-input`, `cli.export.exception` as `'cli-path'`. Update `whyDidThisFailReachability.test.ts` enum-validation logic. Update SKILL.md doc paragraph if it enumerates the values.

**Why.** The 3-way split (engine-path / direct-lowerer-only / reserved) was designed for engine codes; CLI codes don't fit. They aren't engine-path (the engine never emits them), they aren't direct-lowerer-only (lowerer doesn't emit them), and they aren't reserved (they actively fire). Adding `'cli-path'` is the honest fix.

### A6 — `OcctBackend.mirror` JSDoc cleanup (closes N-7)

**Decision.** Strip the "Task 2 / Task 3" plan-task references from `OcctBackend.mirror`'s JSDoc. Replace with stable references ("see `Shape.mirror` in `src/capture/proxy.ts`" or just delete the cross-reference if unnecessary).

**Why.** Plan-task numbers are ephemeral. A reader in rc.20 can't decode "Task 2 of which milestone?" Stable references survive milestones.

### Component 1 — `export_stl` MCP tool (closes F1, F2, F3, F4)

**Where.**
- Create: `src/mcp/tools/exportStl.ts` — the tool implementation. Reads `file` or `code`, runs the export pipeline (via existing CLI logic at `src/cli/commands/export.ts` or wherever STL export lives), writes to `output_path`, returns receipt.
- Modify: `src/mcp/server.ts` — add `export_stl` to the TOOLS array. Update the request handler switch.
- Modify: `src/skill/SKILL.md` — add `export_stl` to the MCP Companion section's tool list.
- Modify: `tests/unit/skill/skillToolCountDrift.test.ts` — count goes from 13 to 14 (the sentinel verifies this automatically; SKILL.md update is the load-bearing edit).
- Create: `tests/integration/mcp/exportStl.test.ts` — round-trip test.

**API shape.**

```typescript
interface ExportStlInput {
  file?: string;
  code?: string;
  output_path: string;
  feature_id?: string;  // optional: which feature to export (defaults to last)
}

interface ExportStlOutput {
  ok: boolean;
  output_path?: string;
  byte_count?: number;
  feature_count?: number;
  diagnostics?: CompilerDiagnostic[];
  error?: string;
}
```

**Error cases:**
- Missing both `file` and `code` → returns `ok: false, error: "Must provide either { file } or { code }."` (no STL written)
- Missing `output_path` → returns `ok: false, error: "Required: output_path"`
- Script lowering fails → returns `ok: false, diagnostics: [...]` (no STL written; diagnostics carry the underlying failure)
- File write fails (permission, missing directory) → returns `ok: false, error: "Cannot write to <path>: <reason>"`
- All other paths: STL written, `ok: true, output_path, byte_count, feature_count`

**Pipeline reuse.** The existing CLI export command at `src/cli/commands/export.ts` (or wherever it lives — plan-time discovery) already runs script → engine → lowerer → STL. The MCP tool can reuse that helper directly; if it isn't currently extracted, the plan extracts it into a `src/script-runtime/exportStl.ts` shared between CLI and MCP.

**Test coverage.**
- Round-trip: build a 10x10x10 box, export to a temp file, assert file exists + byte_count > 0 + valid STL header.
- Error case: malformed code → no file written + diagnostics returned.
- Feature-specific export: build multi-feature script, export with `feature_id` set, assert the right feature was exported.

## Open questions for the spec reviewer

1. **`exportStl` shared helper.** The CLI's `export stl` command and the new MCP tool need shared logic. If the existing CLI command's logic is already factored into `src/script-runtime/exportStl.ts` (or similar), great — both just call it. If not, the plan extracts it as the first task's prep step. Verify file paths during plan-writing.

2. **Component 2 validator parameter shapes.** `Shape.scale` currently accepts `(sx, sy?, sz?)` per `listApi.ts`. The validator needs to accept either a single positive finite number (uniform scale) or three positive finite numbers (per-axis). `Shape.rotate` accepts `(axis, degrees, pivot?)` — pivot validation too? Plan-time judgment.

3. **The `feature.transform.invalid-mirror` code (Component 2).** The mirror-feature-path already emits `feature.mirror.invalid-plane`. The transform-time variant is redundant — Shape.mirror creates a feature, not a transform, so there's no "transform-time mirror invalid plane" path. **The mirror validator is unnecessary; only translate/rotate/scale/reflect get capture-time validators.** Plan should resolve this on read.

These don't block plan-writing; the plan resolves at task time.
