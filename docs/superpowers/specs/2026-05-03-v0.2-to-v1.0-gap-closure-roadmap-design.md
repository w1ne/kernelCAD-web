# v0.2-to-v1.0 Gap-Closure Roadmap — Design Spec

**Status:** design (pre-implementation)
**Date:** 2026-05-03
**Owners:** kernelCAD core
**Related:** `2026-04-29-kernelcad-NORTHSTAR.md`, `2026-05-02-v0.1.0-northstar-rebaseline-design.md`, `2026-05-02-agent-eval-harness-design.md`, `2026-05-02-v0.2.0-tracked-face-refs-design.md`

**Goal:** Close every remaining NORTHSTAR module gap from v0.2 through v1.0 in a single 1-month sprint under solo + AI-augmented parallel-agent execution. Each minor-version bump corresponds to one NORTHSTAR module's gap fully closed, no exceptions, per the strict re-baseline rule established at v0.1.0. The corpus of agent-evaluable tasks grows alongside the modules; coverage gates measure aggregate progress; per-module ship gates honor NORTHSTAR's binary semantic.

**Architecture:** Roadmap-of-roadmaps. This document inventories 24 workstreams, sequences them via dependency graph and examples-driven priority, defines coverage gates, exit criteria, kill criteria, milestone reevaluation cadence, parallel-execution policy, visual demo discipline, and the spike that gates the image-to-CAD module. Each workstream gets its own follow-up brainstorm → spec → plan → execute cycle; this doc is the meta-spec, not the per-module designs.

**Tech Stack:** No additions at the roadmap level. Per-workstream specs may add. The eval harness lands first (already in flight on `feat/eval-harness-v1`); every coverage gate and per-module ship gate depends on it.

**Spec lineage:** Implements the gap-closure roadmap that the v0.1.0 re-baseline spec explicitly queued: *"Gap-closure roadmap document (covering tracked refs / hole / cut / constrained sketches / assemblies / sheet metal / SDF / wood / etc.) — separate brainstorm + spec, queued after v0.1.0 ships."* This is that doc. NORTHSTAR remains the architecture vision; this doc is the path from v0.2 to v1.0 within that vision.

---

## Why this milestone

After v0.1.0 shipped to npm on 2026-05-02, kernelCAD has a clean strict-re-baseline numbering line and a published artifact agents can install. What it doesn't have:

- A multi-version sequencing doc tying NORTHSTAR's module roadmap to the practical 1-month delivery window
- A concrete corpus that the eval harness can grow into
- A parallel-execution policy that lets ~20 workstreams run concurrently without merge collisions
- Coverage and kill gates that turn the strict re-baseline rule from a slogan into an operational discipline
- Visual demo discipline so every iteration produces something showable, not just a green CI badge

This doc closes those gaps so the v0.2 → v1.0 sprint can run with crisp checkpoints and known descope policy.

The four anchor properties from the v0.1.0 strategic positioning carry forward unchanged: **open**, **MCP-native**, **AST-edit-primacy**, **diagnostic-rigorous**. The roadmap below is sequenced to deepen each, not just close feature gaps.

1. **Lock the workstream inventory** for v0.2 → v1.0. Every NORTHSTAR module gets a workstream; every cross-cutting concern from the SOTA review gets a workstream; nothing else.
2. **Lock the corpus shape** the eval harness will grow into — count, layer split, coverage matrix, difficulty bands, sourcing process.
3. **Lock coverage gates and per-module exit criteria** so descope decisions are deterministic, not improvised.
4. **Lock parallel-execution policy** — worktrees, branches, PR cadence, code-review gates, regression policy, integrator role, MCP surface expansion target.
5. **Lock kill criteria + milestone reevaluation cadence** so the sprint stays self-correcting.
6. **Lock the vision spike** (Phase 0 research that gates the v0.16 image-to-CAD module).
7. **Lock cross-cutting policy** — performance floors, API stability, cost budget, materials, persistent format, public-launch automation, visual demo discipline.

## Non-goals (this milestone)

- Per-module API design (deferred to per-workstream brainstorm sessions)
- Per-task corpus content design (deferred to corpus-expansion workstream + per-workstream specs)
- Implementation of any module (deferred to per-workstream plans + dispatched agents)
- Renumbering or restructuring NORTHSTAR (NORTHSTAR remains canonical; this doc plans within it)
- Public marketing / launch positioning beyond what v0.1.0 already established (see anchor properties)
- A calendar — coverage-gated milestones, not date-gated (per design decision below)

## Anchors carried forward (non-negotiable)

From `2026-05-02-v0.1.0-northstar-rebaseline-design.md` §A9, four anchor properties define kernelCAD's distinct positioning. Every workstream in this roadmap is evaluated against these:

1. **Open** — full source under MIT. No closed plugins, no proprietary extensions creeping in, no telemetry without consent.
2. **MCP-native** — agents drive the platform via a persistent MCP server with introspection tools, not one-shot CLI per query. Every workstream that adds capability also adds the MCP surface to expose it.
3. **AST-edit-primacy** — every script-modifying operation (UI, MCP, future plugins) is an AST edit to the canonical `.kcad.ts`. Direct IR mutation remains forbidden per NORTHSTAR Q6b. New mutation surfaces, if any, route through `add_feature` / `set_param_value` / `remove_feature`.
4. **Diagnostic-rigorous** — every emitted diagnostic code has a structured HINTS entry, structurally enforced by the existing CI sentinel. Every new code added by any workstream gets a HINTS entry; the sentinel must remain green.

Per NORTHSTAR risk #3: **Core invariants never descope. Modules can be cut. Discipline cannot.**

## Corpus design

The corpus is the spine. Per the examples-driven sequencing rule, every workstream's "done" requires its corpus tasks pass GATE.

### Target

- **~55 tasks at v1.0.**
- **Two layers, kept distinct internally:**
  - **Parity floor (~10 tasks)** — internally references established CAD parametric benchmark conventions; repo files describe each task as a native kernelCAD task. The parity-floor task list is captured in an internal lineage memory; the public artifacts are the prompts and harnesses themselves.
  - **Differentiator overlay (~45 tasks)** — designed against the four anchor properties + per-module gap closure.

| **Total** | **~55** | |

### Difficulty bands

Every task tagged `easy` / `medium` / `hard`. v1.0 ship gate: 100% of `easy` + 100% of `medium` + ≥60% of `hard`. Hard tasks are aspirational — they're how the agent surface scales beyond the floor.

### Sourcing process

- **Parity-floor tasks**: written from spec/observation only — no copy-paste from any external source. The internal mapping (which kernelCAD task corresponds to which external benchmark for our own audit purposes) lives in lineage memory, not in repo files. Repo task files frame everything as native kernelCAD per the no-comparator-reference policy.
- **Differentiator-overlay tasks**: designed against the four anchor properties. Each task's `prompt.md` includes a private comment header naming which anchor property it exercises (internal note for authors, agents see only the rendered prompt body).

### Where it lives

Per the eval harness v1 spec, tasks live at `eval/tasks/<task-id>/` with `prompt.md` + `harness.ts` + optional `solution-expert.kcad.ts`. Reference solutions are the secondary corpus — hand-written examples that double as `examples/` material and feed the public demo gallery.

### Cadence

Continuous, gated by module availability. New tasks added as modules land. No batch-up-front design.

### Corpus "done at v1.0" criterion

1. Each module has ≥ its target task count above.
2. 100% of `easy` + 100% of `medium` tasks + ≥60% of `hard` tasks pass GATE in the harness against the default model (the difficulty-band rule above; G4 ship gate echoes this).
3. ≥60% of all tasks pass against at least one alternate model (per H4: model-agnostic interface is a v1.0 hard requirement).

## Coverage gates

Coverage = % of corpus tasks passing GATE in the harness against the default model. Aggregate progress signals; per-module ship gates run independently per the strict re-baseline rule.

| Gate | Coverage | Tasks passing (of ~55) | Approximate NORTHSTAR state |
|---|---|---|---|
| **G1** | 10% | ~6 | v0.2 closed + dent in v0.3/v0.4 |
| **G2** | 30% | ~17 | ~5 modules closed: v0.2, v0.3, v0.4, v0.5, v0.7 NURBS |
| **G3** | 70% | ~39 | ~12 modules closed; only long-tail (sheet metal, SDF, vision, GCode, wood, viewport) remain |
| **G4** | 100% | all | v1.0 ship gate |

### Per-gate triggers (decision points, no calendar)

- **G1 (10%):** pre-flight check that harness + corpus + agent loop work end-to-end. Triggers full-scale parallel agent dispatch on independent modules (v0.6, v0.13, v0.14).
- **G2 (30%):** mid-roadmap reevaluation. Descope decision per Kill Criteria. If G2 is missed cleanly, weakest 2–3 modules cut to v1.1+.
- **G3 (70%):** polish-phase entrance. Shift agent capacity to v1.0 polish + docs + corpus close-out for shipped modules. Anything not landed by G3 is at high risk for v1.0 cut.
- **G4 (100%):** v1.0 ship gate. Triggers tag, npm publish, GitHub release, public announcement.

### v1.0 ship gate (G4) precision

The G4 gate is met when all of:

1. **100% of `easy` + 100% of `medium` corpus tasks + ≥60% of `hard` corpus tasks** pass GATE in the harness against the default model over 3 retry attempts (per difficulty bands in Corpus design). Hard tasks below the 60% threshold are aspirational and do not block ship; they roll forward as v1.1+ stretch goals.
2. ≥60% of all corpus tasks (across all difficulty bands) pass against at least one alternate model (per H4).
3. For each NORTHSTAR module v0.X, its module-specific tasks pass GATE at the difficulty-band thresholds (per-module re-baseline rule).
4. v1.0 polish workstream complete (docs site live, CHANGELOG closed, README polished, anchor-property positioning re-affirmed).
5. No diagnostic code lacks a HINTS entry; CI sentinel green.
6. SKILL.md + drift sentinels green.
7. Smoke test on clean container passes for `npm install -g kernelcad@1.0.0`.
8. Visual demo set committed under `docs/demos/v1.0/` per H11.

### Per-module ship gate (recursive)

Each `v0.X.0` ships when:

1. All of that module's corpus tasks pass GATE in the harness against the default model.
2. Its design spec exists at `docs/superpowers/specs/`.
3. Its implementation plan exists at `docs/superpowers/plans/`.
4. Code-reviewer agent has reviewed it and the review has been responded to.
5. CHANGELOG entry written; the strict re-baseline semantic ("v0.X.0 = module X gap closed, no exceptions") respected.
6. Visual artifact set committed under `docs/demos/v0.X/` per H11.

## Parallel-execution policy

### Topology

- **Controller:** the human author. Single integrator.
- **Workstreams:** 24 (per inventory above).
- **Worker pool:** Claude Code agents dispatched via `superpowers:dispatching-parallel-agents` and `superpowers:subagent-driven-development`.
- **Concurrency:** unbounded in principle; bounded in practice by review bandwidth and merge-conflict surface. Recommend ≤4–5 active workstreams at once early; ramp up after harness on `develop` proves stable.

### Worktrees + branches

- Each workstream runs in a dedicated git worktree per `superpowers:using-git-worktrees`. Default location: `~/projects/kernelCAD-web-worktrees/v0.X-<short-name>/`.
- Branch naming follows existing convention: `feat/v0.X-<short-name>` (e.g. `feat/v0.6-assemblies`, `feat/v0.13-sheet-metal`). Established by `feat/v0.2.0-tracked-face-refs`, `feat/eval-harness-v1`, `ui/studio-split-shell`.
- All branches off `develop`. All PRs target `develop`. Merges to `main` only at v1.0 release.

### PR + merge cadence

- One PR per workstream. PR title: `feat(v0.X): <module name>`.
- Dependency order respected at merge time: v0.2 before v0.3, v0.6 before v0.10's joints/explode views, etc. PRs can be opened in any order; merges follow the dependency graph.
- Each PR must include: spec under `docs/superpowers/specs/`, plan under `docs/superpowers/plans/`, code, tests, harness corpus tasks, CHANGELOG entry, visual artifacts under `docs/demos/v0.X/`.

### Two-pass code-review gate (per PR, mandatory, non-negotiable)

1. **Automated:** `superpowers:code-reviewer` agent dispatched on the PR diff. Reviews against the workstream's spec/plan + project standards. Findings logged to PR comments.
2. **Human:** controller addresses blocking findings, merges.

### Regression policy

- Eval harness on `develop` is the cross-workstream regression signal.
- Pre-merge gate: PR's branch must pass every corpus task already green on `develop`, plus add its module's new tasks (which must pass GATE).
- Post-merge: integrator re-runs full harness on `develop` head. Any new failure: fix-forward (open follow-up PR same day). No silent green-to-red flips.

### Cross-workstream API arbitration (integrator role)

When two workstreams touch the same surface (v0.6 assemblies + v0.13 sheet metal both extend `FeatureKind`; v0.4 constraints + v0.5 Studio UI both touch sketch state), controller is sole arbiter. Cross-workstream API decisions get logged to a running file at `docs/superpowers/cross-workstream-decisions.md` (single append-only file, dated entries, easy to search). Per-workstream agents must check the log before designing API surface that could conflict; this is stated as a constraint in their dispatch prompt.

## Kill criteria + descope policy

### Hard rule

> **Core invariants never descope. Modules can be cut. Discipline cannot.**

The four anchor properties and the strict re-baseline rule are non-negotiable. If we slip, modules slip — semantics don't.

### Descope order (riskiest-first, cut from the bottom)

When a coverage gate is missed, modules get cut in this order. Cuts are sticky — once cut from v1.0, the module ships in v1.1+ as its own milestone, not back-folded into the sprint:

1. v0.15 Wood — niche helpers, smallest cut
2. v0.14 SDF — research-heavy, smooth-boolean lib choice open
3. v0.13 Sheet metal — biggest implementation surface
4. v0.10 Viewport extras (cutPlane / explodeView / animation) — cosmetic; jointsView stays gated to v0.6 anyway
5. v0.9 Toolbox lib — user-space scripts; can ship as separate npm package post-v1.0
6. v0.17 GCode — toolpath generation is its own research surface
7. v0.8 BOM/drawings — non-blocking for the agent-first thesis
8. v0.7 NURBS curves — sweep+loft already cover most use cases
9. v0.16 Vision — kept high in the order because it's the stated end goal; cut only if eval gates demand

**Never cut:** v0.2, v0.3, v0.4, v0.5, v0.6, Patterns, v0.11/12 finish, all four SOTA cross-cutting workstreams.

### Gate-based triggers

| Gate slip | Action |
|---|---|
| **G1 missed (10%)** | Pause new dispatch. Audit harness + corpus. Descope #1 (wood) and re-evaluate. If not recoverable in 3 days of focused work, escalate to controller for re-scoping the entire sprint. |
| **G2 missed (30%)** | Descope #1–#3 (wood + SDF + sheet metal). Move to v1.1 candidates. CHANGELOG note: "v0.13/14/15 deferred." |
| **G3 missed (70%)** | Descope #1–#5 (#1–#3 + viewport extras + toolbox lib). Focus all remaining capacity on v1.0 polish + corpus close-out for shipped modules. |
| **G3 missed by >20pp** | Descope #1–#7 (add GCode + BOM/drawings). Ship v1.0 with reduced surface but every shipped module fully solid. |

### Per-workstream kill criteria

**Vision spike (#20):** ≤7 days. Go criterion: ≥1 of 3 difficulty-tier-1 image-to-sketch tasks works on a frontier VLM with depth/normal pre-pass, no fine-tuning. No-go: written assessment pushes v0.16 entirely to v1.1+.

**Visual verifier (#21):** Go criterion: rendering pipeline + VLM-critique loop demonstrates ≥10pp improvement on a 5-task subset against the text-only retry baseline within 5 days. No-go: workstream pivots to "research note + revisit at v1.1"; saved capacity goes to corpus expansion.

**Cookbook (#22):** No kill criterion — continuous and additive. Shipping fewer entries is a soft cut.

**Proactive clarification (#23):** Go criterion: clarification step demonstrably improves hard-task pass rate by ≥5pp without regressing easy/medium tasks within 3 days. Below: ship as opt-in (`--clarify`) only, not default.

**Public benchmark submission (#24):** Go criterion: kernelCAD ranks ≥4th of submitted models on the public leaderboard at submission time. Below 4th: still ship the submission; v1.0 announcement does not lead with the ranking.

### Reversibility rule

A descoped module can be re-promoted mid-sprint only if a hard upstream blocker disappears. Re-promotion needs explicit controller approval and a brief written rationale appended to the cross-workstream-decisions log.

### Mechanical descope procedure

1. Descoped module's spec/plan stays in `docs/superpowers/specs/` and `docs/superpowers/plans/` — not deleted.
2. CHANGELOG.md gets a `## Deferred from v1.0` entry naming the module + rationale + intended next milestone (v1.1, v1.2, etc.).
3. NORTHSTAR's Module Roadmap table gets a footnote noting the module shipped in vX.Y, not v1.0.
4. Any in-flight worktree for the descoped module is paused, not deleted. Branch stays.
5. Corpus tasks for that module remain in `eval/tasks/` but tagged `@deferred-v1.X` so they don't count toward G4.

## Milestone reevaluation cadence

### When

Mandatory reevaluation at every gate transition: **after G1**, **after G2**, **after G3**, **after G4**, and **after every per-module ship** (each `v0.X.0` tag). Plus optional ad-hoc reevaluations triggered by external events (a competitor ships an MCP server; new SOTA paper drops; public benchmark ranking shifts; a user reports a real-world failure).

### What gets reevaluated (six axes, every time)

1. **Direction.** SOTA shift since the last gate (re-run a SOTA research agent; compare against frozen snapshot from this brainstorm). Public-benchmark leaderboard delta. Are the four anchor properties still differentiated, or has someone else shipped MCP / AST-edit / diagnostic-rigor in the interim? Is examples-driven still the right ordering rule, or has a real workflow surfaced that demands a different cut?
2. **NORTHSTAR validity.** Any module that should be added (per the "we can expand NORTHSTAR" rule), removed (per descope), or reordered? Any v1.1+ candidate that should be promoted into v1.0 because a dependency landed cheap? Cross-workstream-decisions log review — any decisions that need to flip?
3. **Code organization.** File-size scan: any file > 500 LoC that should split? Module-boundary scan: tangled responsibilities? Dead-code scan: type-stubs / commented-out paths / unused exports? Test health: harness corpus tasks all green on `develop`? Unit/integration test pass rate? Flake rate? Performance: re-eval latency vs. floor (H1)? Type debt: `any`s, `@ts-expect-error`s vs. previous gate?
4. **Capacity / pace.** How many parallel workstreams sustainable next phase? Any subagent dispatch pattern failing? Are PRs landing fast enough to keep `develop` ahead of upstream regressions?
5. **Anchor-property discipline.** Each new module's MCP-tool surface — does it respect AST-edit-primacy? Are mutations going through existing AST tools or did someone sneak in direct-IR mutation? Diagnostic-rigor: every new error code has a HINTS entry; sentinel green? Open: still genuinely open (no closed plugins, no proprietary extensions creeping in)?
6. **Show what shipped.** Visual demo set since last gate exists and is committed? Per H11, no demo = no per-module ship gate met. If a workstream shipped without a demo, that's a 🔥 blocker.

### Output artifact

Each reevaluation produces one file at `docs/superpowers/reevaluations/2026-MM-DD-after-<gate>.md`. Fixed template per six axes (committed at start of sprint as a stub), freeform within each axis. Each axis gets:

- ✅ "no change" (one line, justified), or
- ⚠️ "issue identified" + concrete action (with workstream owner + due date), or
- 🔥 "blocker" + immediate stop-and-resolve (halts new dispatch until resolved).

### Who does it

Controller with one Explore agent dispatched in parallel to do the SOTA-delta + benchmark scan + code-health scan. Controller synthesizes, writes the file, posts findings to the cross-workstream-decisions log if any decision flips.

### Hard rule

> **No gate transition without a written reevaluation.** If the reevaluation doc isn't committed, the next phase doesn't start.

### First reevaluation

Run a "G0 reevaluation" immediately after the v0.2 tracked-refs ship + harness v1 ship. First natural inflection point; validates cadence works before it's load-bearing.

## Vision spike (Phase 0) + v0.16 module gating

### Spike scope (≤7 days, one agent's effort)

**Goal:** Decide whether image-to-CAD is achievable with off-the-shelf VLMs in the 1-month window, or whether v0.16 module work pushes to v1.1+.

**Pre-pass research.** Read recent academic work on depth/normal map preprocessing for VLM line extraction. Confirm the documented advantage over raw RGB on textureless CAD inputs.

**3-task tier-1 test set:**

- **T1 (easy):** Hand-drawn orthographic line drawing of an L-bracket (single view, dimensioned)
- **T2 (medium):** Photograph of a 3D-printed L-bracket on a flat surface (single view, no dimensions)
- **T3 (hard):** Photograph of a real-world bracket-on-shelf with mild perspective + lighting variation

Each task: input image + a target `.kcad.ts` reference solution that produces a model close to the input.

**Four approaches in parallel:**

- **A) Frontier VLM, raw image, single shot** — image → sketch JSON → extrude script. Baseline, no preprocessing.
- **B) Same VLMs with depth/normal preprocessing** — run input through depth-estimation model, derive normals, hand both to VLM along with original image.
- **C) Two-stage pipeline** — VLM extracts polylines → second VLM call infers extrude direction + parameters from polylines + original image.
- **D) Agent-loop variant** — drive an MCP-equipped agent that can call `extract_polylines`, `propose_extrude`, `evaluate_script` iteratively with diagnostic feedback.

Run each approach against 3 tasks. Score with relaxed harness: pass = produced script evaluates clean + bbox matches reference within 20% on each axis + face count within 50%. Tier-1 is feasibility, not parity.

### Exit criteria

| Outcome | Trigger | Action |
|---|---|---|
| **Strong go** | ≥2 of 3 tasks pass with at least one approach, on a frontier VLM, no fine-tuning | Promote v0.16 to "in scope for v1.0." Spike output becomes v0.16 spec foundation. Brainstorm v0.16 module design begins immediately. |
| **Weak go** | 1 of 3 tasks passes (typically just T1 — orthographic line drawing) | v0.16 ships v1.0 with **scope reduced to orthographic line drawings only**. T2/T3 photo-class deferred to v1.1+. Brainstorm a narrowed v0.16 spec. |
| **No-go** | 0 of 3 tasks pass after 7 days | v0.16 entire module pushes to v1.1+. Spike output becomes a written research note (`docs/superpowers/research/2026-XX-XX-vision-spike-no-go.md`) detailing what was tried, what failed, what the next viable approach would need. The 7 days inform v1.1+. |

### What the spike does NOT do

- **No fine-tuning.** Out of scope; spike answers feasibility with frontier VLMs only.
- **No multi-view photogrammetry.** Single-view only; multi-view reconstruction is v2+ scope.
- **No real-time camera input.** Static images only.
- **No new MCP tools yet.** Tools land with v0.16 module work, post-spike.

### Spike artifact

Whether go or no-go, the spike produces one written deliverable in 7 days at `docs/superpowers/research/2026-XX-XX-vision-spike-report.md`. Format pre-templated. The report drives the gate decision; committed regardless of outcome.

## Roadmap policy

Cross-cutting policy items that apply uniformly across all workstreams.

### H1 — Performance floors

**Floor:** Parametric re-eval ≤ 200ms for small param changes on 100-feature models (per NORTHSTAR risk #2). Full harness corpus run ≤ 30 min on default model. Per-task harness eval ≤ 60s. Cold-start `kernelcad evaluate` ≤ 2s on a 10-feature script.

**Enforcement:** harness records `time_ms` per task. Reevaluation cadence axis #3 checks for regression vs. previous gate. >5% slower triggers a code-organization issue.

**Above the floor:** no perf optimization for the 1-month sprint. Floors are *don't-regress* gates, not *make-faster* targets.

### H2 — API stability

**Pre-v1.0:** every change is fair game. v0.1.0's published syntax (`param`, `box`, `cylinder`, `sphere`, `extrude`, `revolve`, `sweep`, `loft`, `fillet`, `chamfer`, `shell`, `mirror`, `reflect`, `path`/`lineTo`/arc variants, `subtract`/`union`/`intersect`, `translate`/`rotate`/`scale`, `.label()`, `selectEdges`) is best-effort-no-break. If a change breaks `examples/bracket-with-hole.kcad.ts`, the workstream owns a migration script.

**At v1.0.0 ship:** strict semver. Breaking changes only at v2.0+. The four anchor properties become permanent invariants.

### H3 — Cost budget

**Projection:** ~2.6M tokens per full corpus run (~55 tasks × ~3 attempts × ~16K tokens). Multi-model runs (alternate models for H4) ≈ 3× that. Roughly $30 per single-model corpus run, ~$90 per multi-model run.

**Budget:** **$5,000** for the 1-month sprint. Tracks: API costs, embeddings, vision-model calls. Excludes: cloud infra, unrelated subscriptions.

**Enforcement:** cost recorded per harness run; reevaluation cadence checks against linear-burn projection. >2× projection triggers a halt + audit.

### H4 — Model-agnostic LLM interface (v1.0 hard requirement)

Any LLM provider must be pluggable — the harness already runs on the Anthropic SDK; v1.0 hard requirement is that swap to another provider (OpenAI, alternate frontier, local-via-Ollama) is configuration, not code change. Default provider = the harness's current default. Fallback chain configured in env.

### H5 — Materials / appearance

**In-scope for v1.0:** material tags on `FeatureRecord.metadata` (string keys: `material`, `qty`, `partNumber`). BOM export reads these. Folds into v0.8.

**Out-of-scope for v1.0:** PBR rendering, material libraries, appearance overrides per face, texture maps. v1.1+ candidate.

### H6 — Persistent binary format

NORTHSTAR explicitly defers (`.kcad.ts` + optional `.kcad.json` is the only saved-artifact contract; recompute-on-load).

**Out-of-scope for v1.0.** v1.1+ candidate gated on real-world load-latency measurement.

### H7 — Per-module ship → public-launch automation

**Each `v0.X.0` ship:**
- Git tag + GitHub Release (mandatory, non-skippable)
- npm publish (controller-discretion gate per v0.1.0 precedent)
- CHANGELOG entry (mandatory)
- Tweet / blog post (controller discretion)

**At v1.0.0 ship:**
- All of the above
- Plus: blog post mandatory, public-benchmark submission landed (workstream #24), public docs site live (folded into v1.0 polish)

### H8 — Test-coverage threshold

**No line-coverage threshold.** Harness GATE on the corpus is the meaningful test gate. Existing unit + integration test suites continue to gate per-PR (must remain green); harness gates per-module ship.

### H9 — Public examples + demos gallery

Folds into v1.0 polish workstream. Renders each corpus task's reference solution (where one exists) with screenshot + code + harness score. Generated, not hand-written. Lives at `docs/examples/index.html` or a gh-pages branch — controller picks. Becomes the public landing page for the demo set built up across the sprint.

### H10 — Documentation discipline (per anchor property #4)

Every new diagnostic code added by any workstream must:

1. Get a HINTS entry (existing CI sentinel enforces; must remain green).
2. Get a SKILL.md mention (existing drift sentinel enforces; must remain green).
3. Get at least one corpus task that exercises the recovery path (new requirement; adds to workstream definition-of-done).

### H11 — Per-iteration visual artifact (mandatory)

**Every per-module ship (`v0.X.0`) and every coverage gate (G1–G4) produces a committed visual artifact set:**

1. **Short demo recording** — ≤30s GIF or MP4 showing the agent loop producing a representative part using the new capability. Format: terminal-on-left + 3D render-on-right side-by-side. Captured during a real harness run, not staged.
2. **Side-by-side static panel** — single PNG: prompt text | generated `.kcad.ts` code | rendered model (ortho + iso views) | harness score badge. Auto-generated from harness output.
3. **One-paragraph "what's new"** — markdown blurb explaining the capability gain in plain English (the "show it" copy for tweets, GitHub release notes, blog posts).

**Storage:** `docs/demos/v0.X/` per module; `docs/demos/gates/G<N>/` per gate. Committed to git; binary artifacts committed directly when small or via git-lfs if recordings exceed a few MB.

**Embedded in:** GitHub release notes (mandatory), CHANGELOG entries (markdown image embed), public-benchmark submission notes (workstream #24), public examples gallery (H9).

**Enforcement:** per-module ship gate gains a 6th criterion — "visual artifact set committed under `docs/demos/v0.X/`." No artifact, no `v0.X.0` tag.

### H12 — Demo automation infrastructure (folded into workstream #21)

The visual verifier loop already needs ortho-rendering MCP tools (`render_views`). Same infrastructure produces demo artifacts — no separate workstream:

- `render_views` produces verifier input *and* static panel renders.
- Wrapper (`scripts/captureDemo.ts`) drives the harness on a chosen corpus task with the agent loop visible (terminal capture via `asciinema` or `vhs`), runs `render_views` mid-loop, stitches into a GIF.
- Output template at `scripts/demo-template/` — canonical layout (left: terminal log, right: render).

Effort impact: extends workstream #21's scope by ~1 day of agent work. No workstream count change.

### H12-aux — Demo carve-out for workstream #23

**Proactive clarification** doesn't produce a part — it produces a dialog turn. Its visual artifact is a screenshot of the clarification exchange + the resulting part downstream. Treated as a demo even though it isn't a 3D render alone.

## Out-of-scope, risks, open questions

### I1 — Out-of-scope for v1.0 (explicit)

- B-Rep persistence in saved files
- Native desktop app (`kernelCAD-desktop` is a separate effort)
- Multi-user / cloud sync

**This roadmap also excludes:**

- Persistent binary format / `.kcad-cache` (H6)
- Multi-view photogrammetry, real-time camera input (Vision spike scope)
- Fine-tuning custom models (Vision spike non-goal)
- Public marketing site / docs site beyond gh-pages auto-gen (H9)
- File-format import (no F3D / STEP-to-script transpiler)
- Threads beyond what fits into v0.9 toolbox helpers
- Constraint solver beyond geometric (no kinematic, no dynamic)
- Generative design / topology optimization (separate research direction)

### I2 — Documented v1.1+ candidates

Items the gap-closure roadmap is *aware of* but *not committing to*:

- GCode/CAM beyond 2.5D (full toolpath generation, post-processors, machine kinematics) — if v0.17 gets descoped per Kill Criteria
- Wood / sheet-metal / SDF — if descoped per Kill Criteria
- Custom-trained vision model — if vision spike's no-go report calls for it
- Persistent `.kcad-cache` binary format — if perf measurements demand
- Multi-view photogrammetry
- F3D / STEP / IGES import-to-script transpiler
- Generative / topology-optimization module
- Cloud sync / multi-user collaboration
- PBR materials, texture maps, appearance overrides

CHANGELOG.md gets a `## Deferred to v1.1+` block when v1.0 ships, listing each.

### I3 — Risks (deduplicated)

**High:**

1. **Vision spike no-go.** Pushes v0.16 to v1.1+; stated end goal "create models from pictures" doesn't ship in v1.0. *Mitigation:* spike is time-boxed (≤7 days) and runs parallel; capacity loss is bounded.
2. **Capacity crunch.** 24 workstreams in 1 month is at the upper edge of plausible even with parallel agents. *Mitigation:* descope policy, reevaluation cadence, suggested concurrency cap of ≤4–5 active workstreams early.
3. **Competitor ships MCP for their own DSL mid-sprint.** MCP-native differentiation evaporates. *Mitigation:* ship MCP tool surface fast and deep (face/edge history exposure is a parity gap that takes months to reproduce); reevaluation axis #1 watches for this.

**Medium:**

4. **Eval harness regression / flakiness.** All coverage gates depend on it. *Mitigation:* harness has self-test mode + golden CI fixture per its own spec; reevaluation cadence axis #3 catches drift.
5. **Cross-workstream API conflicts.** Assembly + sheet metal both extend `FeatureKind`; SDF + booleans both touch geometry pipeline. *Mitigation:* cross-workstream-decisions log + integrator arbitration; serialization rule for shared-surface workstreams.
6. **Cost runaway.** $5K projection could 2× under bad retry-loop dynamics. *Mitigation:* per-run cost in `score.json`; reevaluation triggers halt at 2× projection.
7. **Anchor-property drift under velocity pressure.** Agents under deadline pressure invent shortcuts. *Mitigation:* hard rule from Kill Criteria (core invariants never descope), per-PR `superpowers:code-reviewer` gate.

**Low:**

8. **Subagent context loss on long workstreams.** Mitigated by spec → plan → execute discipline (agents execute plans, don't improvise).
9. **SOTA shift mid-sprint.** A paper drops that obsoletes our approach. *Mitigation:* reevaluation axis #1 + roadmap is module-grained so any pivot lands at the next gate, not mid-flight.
10. **Public-benchmark poor showing.** Submission lands ≥4th place per workstream #24 go criterion; below that we still ship but don't lead with the rank.
11. **OCCT WASM upgrade breaks `(shape as any).wrapped` access pattern.** Mitigated by pinned Replicad version (already 0.20.5) + harness regression catches it instantly.
